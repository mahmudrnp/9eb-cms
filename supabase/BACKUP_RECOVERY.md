# BACKUP & RECOVERY — 9 EB CMS (Phase 14)

এই ডকুমেন্ট Supabase-হোস্টেড PostgreSQL ডাটাবেসের ব্যাকআপ ও রিকভারি-স্ট্র্যাটেজি বর্ণনা করে। Phase01 §১০-এর নিরাপত্তা-প্রয়োজনীয়তা ("ব্যাকআপ/রিকভারি স্ট্র্যাটেজি") এখানে পূরণ করা হলো।

## ১. Supabase-এর নিজস্ব বিল্ট-ইন ব্যাকআপ

Supabase প্রতিটা প্রজেক্টে স্বয়ংক্রিয় ব্যাকআপ দেয়, প্ল্যান অনুযায়ী ভিন্ন:
- **Free/Pro প্ল্যান:** দৈনিক স্বয়ংক্রিয় ব্যাকআপ, সাধারণত সাম্প্রতিক ৭ দিন পর্যন্ত রিটেনশন (Pro-তে বেশি হতে পারে)।
- **Pro+ (Point-in-Time Recovery/PITR অ্যাড-অন):** যেকোনো মুহূর্তে (সেকেন্ড-নির্ভুলতায়) রিস্টোর করার সুবিধা — আর্থিক-লেজার সিস্টেমের জন্য এটা **জোরালোভাবে সুপারিশকৃত**, কারণ দৈনিক-ব্যাকআপে দিনের-মাঝের ভুল-এন্ট্রি বা দুর্ঘটনাজনিত ডেটা-ক্ষতির ক্ষেত্রে পুরো দিনের লেনদেন হারানোর ঝুঁকি থাকে।

**অ্যাকশন-আইটেম (POLICY/OPS INPUT REQUIRED):** বর্তমান Supabase প্ল্যান (Free/Pro/PITR-সহ) নিশ্চিত করে প্রয়োজনে PITR চালু করুন — Supabase Dashboard → Project Settings → Backups থেকে দেখা যায়।

## ২. ম্যানুয়াল ব্যাকআপ (সুপারিশকৃত সম্পূরক অভ্যাস)

Supabase-এর বিল্ট-ইন ব্যাকআপের পাশাপাশি, নিয়মিত ম্যানুয়াল `pg_dump` নেওয়ার অভ্যাস রাখা ভালো — বিশেষত **প্রতি মাস-সমাপনীর (Phase11, ২৫ তারিখ) ঠিক আগে**, যাতে ফাইনালাইজেশনের আগের অবস্থার একটা অফলাইন-কপি থাকে।

### প্রয়োজনীয় তথ্য
Supabase Dashboard → Project Settings → Database → Connection string (URI) থেকে সংযোগ-তথ্য পাওয়া যাবে। **এই কানেকশন-স্ট্রিং/পাসওয়ার্ড কখনো কোডে বা রিপোজিটরিতে রাখা হবে না** (Phase01 §১০ নীতি)।

### কমান্ড (স্থানীয় কম্পিউটার থেকে, `pg_dump` ইনস্টল থাকতে হবে)
```bash
pg_dump "postgresql://postgres:[PASSWORD]@[HOST]:5432/postgres" \
  --schema=public \
  --no-owner --no-privileges \
  -F c -f "cms_backup_$(date +%Y%m%d).dump"
```
- `-F c` (custom format) — কম্প্রেসড, `pg_restore` দিয়ে সিলেক্টিভ-রিস্টোর সম্ভব
- ব্যাকআপ-ফাইল নিরাপদ স্থানে (এনক্রিপ্টেড ড্রাইভ/অফলাইন স্টোরেজ) রাখুন — এতে সব সৈনিকের আর্থিক-তথ্য থাকে

### রিস্টোর কমান্ড (দুর্যোগের ক্ষেত্রে, নতুন/খালি Supabase প্রজেক্টে)
```bash
pg_restore --no-owner --no-privileges \
  -d "postgresql://postgres:[PASSWORD]@[HOST]:5432/postgres" \
  cms_backup_20260925.dump
```
রিস্টোরের পরে `supabase/rls_policies.sql`-এর পলিসিগুলো টেবিলের সাথে বহাল আছে কিনা যাচাই করুন (pg_dump সাধারণত RLS পলিসিও কপি করে, কিন্তু auth স্কিমা আলাদাভাবে পরিচালিত হয় — auth.users পুনরুদ্ধারের জন্য Supabase Support-এর সহায়তা লাগতে পারে)।

## ৩. রিপোর্ট-এক্সপোর্ট — একটা সম্পূরক ডেটা-সেফটি-নেট

Phase13-এর CSV/Excel এক্সপোর্ট সুবিধা (ইনভেন্টরি, বিক্রয়, বকেয়া, P&L, খরচ, স্টক-মুভমেন্ট) প্রযুক্তিগত ব্যাকআপ নয়, কিন্তু ব্যবহারিকভাবে একটা মূল্যবান অতিরিক্ত সুরক্ষা — মাসিক-ভিত্তিতে গুরুত্বপূর্ণ রিপোর্ট এক্সপোর্ট করে অফলাইনে সংরক্ষণ করলে (Google Drive/লোকাল ড্রাইভ) কোনো ডাটাবেস-বিপর্যয়েও ঐতিহাসিক-তথ্যের একটা মানব-পাঠযোগ্য কপি থাকবে। প্রতিটা এক্সপোর্ট এখন Phase14-এর অডিট-লগেও রেকর্ড হয় (`/audit`)।

## ৪. দুর্যোগ-পুনরুদ্ধার পরিকল্পনা (সংক্ষিপ্ত)

|---|---|
| ভুল এন্ট্রি/দুর্ঘটনাজনিত সমস্যা | Phase01 নীতি: correction-entry — কখনো সরাসরি ডেটা-এডিট না |
| Supabase প্রজেক্ট দুর্ঘটনাক্রমে মুছে গেলে/অ্যাক্সেস হারালে | সাম্প্রতিক PITR/দৈনিক-ব্যাকআপ থেকে রিস্টোর, অথবা সর্বশেষ ম্যানুয়াল `pg_dump` থেকে নতুন প্রজেক্টে রিস্টোর |
| RLS পলিসি ভুলবশত মুছে/পরিবর্তিত হলে | `supabase/rls_policies.sql` + `phase14_audit_security.sql` পুনরায় রান করুন (idempotent না — আগে `DROP POLICY IF EXISTS` দিয়ে পরিষ্কার করে নিন) |
| `.env`/সিক্রেট ফাঁস হলে | Supabase Dashboard থেকে anon/service key rotate করুন, `.env` আপডেট করুন, পুরনো key তাৎক্ষণিক invalid |
